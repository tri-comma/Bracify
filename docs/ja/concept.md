# コンセプトと設計原則

[← ドキュメント一覧](./README.md) | 言語: **日本語** | [English](../en/concept.md)

Bracify の機能はすべて、このページの原則に沿って設計します。新しい機能の提案（Issue）と実装は、末尾の「機能を提案するときの確認項目」を満たす必要があります。

## 想定する利用者

| 利用者 | できること | できないと考えること |
|---|---|---|
| **IT に詳しくないエンドユーザー**（判断の基準） | HTML を書く・直す、テンプレートを選ぶ、画面の指示に従ってボタンを押す、Web サービスのアカウントに入力する | ターミナルでのコマンド操作、環境変数の設定、設定ファイルの手書き、サーバー・DB・メールサーバーの準備、JavaScript を書くこと |
| **ライトな Web エンジニア**（マークアップエンジニアなど） | 上記に加えて、HTML / CSS を自在に書く、手順書どおりに作業する | 上記と同じ。できても、させない |

機能はエンドユーザーが使える形を基準に設計します。「エンジニアなら使える」は、主要な機能の説明として不十分です。

## 設計原則

1. **HTML だけで作れる**: 機能は HTML のタグと属性で宣言します。JavaScript を書かないと使えない機能は作りません。
2. **ターミナル不要**: 作成・プレビュー・データ管理・設定・公開・更新まで、Bracify Studio の画面で完結します。
3. **利用者が決める設定は Studio の画面で行う**: 環境変数、設定ファイルの手書き、DB の直接編集を利用者に求めません。設定は [設定一覧](./settings.md) に登録し、プロジェクトと一緒に保存・公開されるようにします。環境変数は、エンジニアが上書きするための手段としてだけ用意します。
4. **外部サービスの準備を前提にしない**: メールサーバー、API キー、特定のクラウドのアカウントなどを利用者が用意しないと動かない機能は作りません。どうしても必要な場合は、Studio が画面で手順を案内し、用意しなくても基本の動作はするようにします。
5. **安全が既定**: 宣言や設定を忘れたときは、安全な側（公開しない、書き込ませない、上限をかける）に倒れます。
6. **特定の環境に縛らない**: 特定のホスティング業者、コンテナ、OS を前提にしません。
7. **SSR と CSR で同じ結果**: 同じ HTML は、サーバー（SSR）でもブラウザ（CSR / ローカルモード）でも同じ結果になります。
8. **作ったものは素の HTML**: プロジェクトはただの HTML とデータです。Bracify をやめても成果物は残り、どこへでも持ち運べます。

## エンジニア向け機能の扱い

JavaScript を書く拡張（フック）、CLI、外部 DB の接続など、エンジニアにしか使えない機能も作ってよいものとします。ただし、次の条件を守ります。

- **任意であること**: 使わなくても、主要な機能（作る・データを保存する・公開する・更新する）はすべて利用できます。
- **明示すること**: ドキュメントで「上級者向け」と明記し、Studio の通常の画面には出しません。
- **主要な機能の代わりにしないこと**: 「エンドユーザーには難しいので、エンジニア向け機能で解決する」という設計にはしません。

## 機能を提案するときの確認項目

Issue の起票時と実装の前に、次をすべて確認します。1 つでも「いいえ」がある場合は、設計を見直すか、「エンジニア向け機能の扱い」の条件を満たすことを Issue に書きます。

1. この機能を、エンドユーザーは **HTML と Studio の画面だけで** 使えるか（ターミナル・環境変数・設定ファイルの手書き・JavaScript が不要か）。
2. 利用者が行う操作を手順として書き出したとき、すべての手順が上記の「できること」に収まるか。
3. 新しい設定がある場合、[設定一覧](./settings.md) に行を追加し、Studio の画面で設定できるようにしたか。
4. 利用者が外部サービス（メールサーバー、API キー、特定のクラウドなど）を用意しなくても動くか。
5. 宣言や設定を忘れたとき、安全な側に倒れるか。
6. 特定のホスティング業者・コンテナ・OS を前提にしていないか。
7. SSR と CSR（ローカルモード）で同じ結果になるか。違う場合は、その理由と制限を書いたか。
