## 開発ルール（全工程共通）

0. **コンセプト適合の原則**
   - すべての機能は `docs/ja/concept.md`（コンセプトと設計原則）に従う。判断の基準は「IT に詳しくないエンドユーザーが、HTML と Studio の画面だけで使えるか」である。
   - 機能の Issue を起票するとき、および実装に着手する前に、`docs/ja/concept.md` の「機能を提案するときの確認項目」をすべて確認し、結果を Issue に書く。「いいえ」がある場合は設計を見直すか、「エンジニア向け機能の扱い」の条件を満たすことを書く。
   - 利用者が変えられる設定を追加するときは、`docs/ja/settings.md`（設定一覧）に行を追加する。行の無い設定（環境変数を含む）を追加してはならない。

1. **ドキュメント優先原則**
   - HTML作成者（ユーザー）に関わるすべての仕様は、必ず `docs/ja/`（日本語・マスター）に記載されていなければならない。英語版 `docs/en/` も同じ内容に保つ。`README.md` は紹介ページであり、仕様の正は `docs/` に置く。
   - `docs/ja/` に記載のない仕様を実装に含めることは禁止。

2. **ドキュメントとコードの分離**
   - `docs/` の修正と、ソースコード（ロジック）の修正を同一のターンで行ってはならない。
   - 手順：
     1. 仕様の提案と合意
     2. `docs/ja/`・`docs/en/` の更新（仕様の確定）
     3. ソースコードの修正（実装）

3. **設計方針**
   - 不要な記法（インデックス指定や独自のエイリアス構文など）は避け、自動判別やシンプルさを優先する。
   - 例：データが1件のみの場合、インデックスを指定せずともアクセス可能にする。

## 開発手順

1. 機能を実装・変更する前に、現在の `docs/ja/` を参照し、`docs/ja/concept.md` の確認項目で設計を点検する。
2. 仕様変更が必要な場合、まずユーザーに提案し、承諾を得る。
3. `docs/ja/`（および `docs/en/`）を更新し、その後のターンで実装に取り掛かる。
4. 実装したソースは全網羅するようにテストコードを実装、テスト実行する。不具合があれば修正とテストを繰り返す。
5. 追加した機能のテストが完了したら、存在するすべてのテストコードを実行する。デグレードが見つかった場合は報告し修正作業を一度中断する。テスト実行がすべて正常終了したら作業完了とする。
